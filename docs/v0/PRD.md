> 版本：**v1.4.0（活规格）** · 最后核对：**2026-10-04**
> 文档定位：**唯一活规格**。功能范围以本文档为准；视觉细节以 [`DESIGN.md`](./DESIGN.md) 为准。
> 产品形态：**macOS 独占**本地桌面应用（Tauri v2）
> 目标平台：开发机 macOS 26.6 及以上 · Apple Silicon M5（仅 arm64）
> 使用范围：**开发者本人自用，不对外分发**
> 一句话定位：**一张纸上的科研学习工作台**——日程与倒计时之外，逐步承载科研学习需要的资料（v1.4 起：文献）；纸张质感，本地存储，完全离线。

## 0. 文档纪律（先读这一节）

### 0.1 四份文档的分工

| 文档 | 视角 | 什么时候动它 |
| --- | --- | --- |
| **本文档 `docs/v0/PRD.md`** | **需求**：要什么 + 验收标准 + 状态 | **任何功能开发的第一步** |
| [`DESIGN.md`](./DESIGN.md) | 视觉与组件规格 | 视觉改动实现后回写 |
| `docs/v1/PLAN-v1.x.md` | 施工图：现状证据、实施、拍板项 | 立项后写；完成后只作历史，不再改 |
| `docs/v1/RELEASE-NOTES*.md` | 版本视角：这版发了什么、迁移、限制 | 每个版本发布时 |
| `docs/DEVLOG.md` | 过程视角：做了什么、被什么绊住 | 每次会话结束 |

### 0.2 硬性顺序（v1.1 的教训）

v1.1 的施工图里写了「完成后**回写** PRD」，执行时没做 —— 于是 `UI-14~UI-24`、`CD-16~18`、`DATA-06` 只活在计划文档里，PRD 的表停在 `UI-08`。为避免重演：

1. **先改 PRD**：新需求先拿 ID（模块前缀 + 序号，不与既有 ID 冲突）、写清需求与验收标准，并登记到 §5.0。**没有进 PRD 的需求不开工。**
2. 再写 `PLAN-v1.x.md`：现状证据（文件:行）+ 实施 + 待拍板项。
3. 实现完成后**回写本文档**：§5.0 状态改为「已实现 vX.Y」，补齐受影响条目与 `DESIGN.md`。
4. 最后才写 `RELEASE-NOTES-vX.Y.md` 与 `DEVLOG.md`。

### 0.3 状态图例与维护点

- 状态只维护在 **§5.0 需求状态总览**一处；`§5.1~§5.8` 只放需求定义，不重复写状态。
- §5.0 取值：`已实现 vX.Y` / `已废弃·被 XX 替代` / `作废编号`。**未实现的需求不写进本文档**（见 §0.4）。
- **每次发布收尾**：更新 §5.0 + 文首「最后核对」（版本号 + 日期）。「最后核对」落后于实际发布线，就说明纪律断了。

### 0.4 内容边界（红线）

- **PRD 只收录用户明确要求或明确确认过的内容**：需求、验收标准、字段、范围都不能超出用户说过的范围。
- **禁止画蛇添足**：不得自行推断「用户大概还想要 X」并写成需求；不得为了文档完整而补路线图、待办池、可能性清单、优先级臆断。
- 需要提建议时**在对话里说**，由用户决定是否立项；未被用户确认的一律不写入本文档。
- 反向也成立：用户划掉的范围**整条移除**，编号登记为作废、不复用；但**已确认的需求可以先写进需求表**（那正是立项），实现后再补进 §5.0 状态总览。

## 1. 产品概述

### 1.1 背景

现有日历/待办工具普遍存在两个问题：

- **倒计时是二等公民**：日历类应用只关心"某天有事"，不关心"距离那天还有多少天"；而倒计时类应用又无法与日程、日历联动，信息孤立。
- **视觉压迫感强**：多数生产力工具是高密度、深色、信息仪表盘风格，长期使用容易疲惫。

RunningDO 把"倒计时"和"日历日程"放在同一个视图里，并用**纸张质感**作为整体视觉语言，降低使用压力、增强纪念感与仪式感。

**v1.4 起的定位扩展**：RunningDO 不再只是日程工具，而是**覆盖科研学习需求的多内容应用**。组织方式：**一个部门一个页面**——「倒计时 + 日历」是同一个部门（日历页），文献是另一个部门（文献页），将来继续增加内容模块时按同一模式扩展。应用名保留 **RunningDO**。

### 1.2 产品目标

| 优先级 | 目标 | 衡量方式 |
| --- | --- | --- |
| 核心 | 5 秒内完成一次倒计时创建 | 新建倒计时 ≤ 2 次输入 + 1 次确认 |
| 核心 | 倒计时与日历双向可视 | 日历上可直接看到倒计时标记，点击可跳转/查看 |
| 核心 | **日历页**一屏之内同时掌握"倒计时"和"日程" | 左栏倒计时 + 右侧日历常驻同屏（同一部门内不互斥） |
| 次要 | 日历具备实用日历能力 | 月视图 / 周视图 / 日视图 |
| 次要 | 日历带农历与节日信息 | 月视图每格显示农历、节气、节日 |
| 次要 | 承载科研学习资料（v1.4 起：文献） | 顶栏独立页面（第四页） |
| 次要 | 纸张风格贯穿全应用 | 统一色板 + 材质 + 组件规范 |

### 1.3 非目标（本期不做）

- 多设备云同步、账号体系、社交分享
- 团队协作、共享日历、会议室预约
- **Windows / Linux / iOS / Android / Web 版本**——本项目为 macOS 独占，不做跨平台适配，允许使用 macOS 专属 API
- 复杂的重复规则可视化编辑器（RRULE 全量支持）
- 第三方日历双向同步（Google / Outlook / CalDAV）
- 写入系统「日历」App（EventKit 双向同步）
- **对外分发**：不做 App Store、不做 Developer ID 公证、不做 `.dmg` 安装向导、不做自动更新（Sparkle）、不做崩溃上报与埋点
- **多用户适配**：不做账号、不做权限分级、不做首次引导流程（Onboarding）
- **多语言**：界面中文即可，不做 i18n 资源切换
- **兼容性妥协**：不为旧 macOS、Intel 芯片、其他屏幕尺寸写兼容分支

### 1.4 目标用户与使用场景

**唯一目标用户：开发者本人。** 本产品不是通用商业软件，需求取舍以「我每天都会用、并且愿意长期用」为唯一标准。

| 维度 | 结论 |
| --- | --- |
| 用户数量 | 1（本人） |
| 使用设备 | 自己的 Mac（macOS 26.6 · Apple M5 · arm64） |
| 部署方式 | 本地构建 → 安装到 `/Applications` → 日常双击启动 |
| 反馈来源 | 自己 |
| 优先级判断 | 「我是否会天天用」>「功能是否完整」>「别人是否觉得好」 |

**个人使用带来的取舍**

- 可以硬编码个人偏好默认值（周起始日、默认视图、时区），设置项只为"可能变"的东西保留。
- 不需要 Onboarding、不需要埋点、可以有"仅我可见"的调试入口。
- 不需要兼容性妥协：内存与启动速度优先于体积与可移植性。
- 不需要为了"看起来专业"而增加任何功能。

**典型一天**

> 早上打开 Mac，左栏看到三个倒计时，右侧月视图上今天有两件事，6 月 7 日格子里有一枚朱砂印章。新增一件事 → 点日历格 → 输入标题 → 点「添加」。关掉窗口去写代码，应用留在菜单栏里，点图标可重新打开。

### 1.5 平台范围（macOS 独占）

**已确认决策**：RunningDO 是 **macOS 独占、开发者自用**的本地应用。不追求跨平台，也不追求分发。允许并鼓励使用 macOS 原生能力（菜单栏、原生菜单、`NSAppearance` 等）。

| 项 | 决策 |
| --- | --- |
| 支持系统 | **macOS 26.6（开发机当前版本）及以上**；不向下兼容 |
| 芯片 | 仅 Apple Silicon（arm64，M5）。**不做 Intel 通用二进制** |
| 签名 | **ad-hoc 签名**（`codesign -s -`），无需 Apple Developer 账号 |
| 公证 | **不做**（本机构建产物无 quarantine 属性，Gatekeeper 不拦截） |
| 分发 | **不对外分发**；本地构建后安装到 `/Applications/RunningDO.app` |
| App Store | 不做 |
| 自动更新 | 不做（要更新就重新构建安装） |
| 窗口策略 | 单主窗口；关闭按钮 = 隐藏窗口并保持菜单栏常驻；从菜单栏选「退出」才真正结束应用 |
| 平台边界 | 不做 Windows / Linux / iOS / Android / Web |

**「自用 + 本地部署」对产品意味着什么**

1. **省掉整条发布链路**：不需要 Apple Developer（$99/年）、不需要公证、不需要 `.dmg` 制作、不需要 Sparkle 自动更新、不需要崩溃上报。省下的时间全部投入功能与手感。
2. **只为一种环境优化**：单一 macOS 版本、单一芯片架构、单一用户。可以放心用原生 API，不用写兼容分支。
3. **但"稳定部署为软件"提出了新要求**：必须能一键构建出**可日常双击运行的 `.app`**，而不是只能 `tauri dev` 跑开发服务器。这需要一条明确的本地构建与安装流程（见 §7.6）。

## 2. 设计原则

1. **纸优先**：界面是"一张纸 + 几张便签"，不是仪表盘。禁止深色科技风、荧光渐变、玻璃拟态。
2. **一眼天数**：倒计时的第一视觉必须是"还有多少天"，其次才是标题与日期。
3. **部门内同屏，部门间可切换**：倒计时与日历同属一个部门（日历页），两者必须同屏常驻，不得做成 Tab、折叠或抽屉互斥；顶栏的不同页面（日历 / 议程 / 文献 / 设置）之间允许切换。
4. **克制的信息**：不堆砌徽章、状态胶囊、伪系统标签。留白承担设计。
5. **本地优先**：全部数据本地存储，离线完全可用，不依赖网络。
6. **指针优先**：所有操作都能用鼠标/触控板点出来，不要求记忆任何快捷键。快捷键只作为系统默认行为的附带结果存在，不作为使用路径。详见 §6.5。

**字体（关键识别特征，不可混用）**

| 层级 | 字体 | 字号/字重 |
| --- | --- | --- |
| 倒计时天数大数字 | **衬线** | `34px / 600` |
| 视图标题（2026 年 6 月） | **衬线** | `28px / 500` |
| 月格日号、周视图列头 | **衬线** | `17px / 500` |
| 卡片标题、事件标题 | **衬线** | `16px / 500` |
| 节日名 | 无衬线 | `12px / 600` 朱砂 |
| 农历 / 节气 | 无衬线 | `11px / 400` 淡墨 |
| 事件行文字 | 无衬线 | `12.5px / 400` |
| 按钮 / 表单 | 无衬线 | `13.5–14px / 500` |

> **一句话记法**：**衬线管标题与数字，无衬线管正文与操作。**

**材质与形态**

- 全局叠加极轻纸张噪点/纤维纹理（透明度 ≤ 5%），不做重噪点。
- 卡片使用**可见纸边**：1px 纸纤维灰描边 + 轻微下沉阴影（`0 1px 2px`）与错位投影。
- 圆角克制：`2 / 4 / 6px`，禁止大圆角（≥12px）与"胶囊化"。
- 允许的装饰元素：胶带、图钉、回形针、手写批注、格线/横线背景、撕纸边、印章。
- 装饰元素必须可关闭（设置项：`纸张装饰`），避免干扰阅读。

**字体**

- 标题/数字：衬线或宋体系（`Noto Serif SC` / `Source Han Serif`），倒计时数字可用等宽衬线。
- 正文/控件：干净无衬线（`Inter` / `Noto Sans SC`）。
- 农历、节气：小号淡墨色无衬线，与公历数字形成层级对比。

**动效（暗示而非炫技）**

- 卡片"贴上"：`float-up + 轻微旋转归位`（180–240ms）。
- 日历翻月：纸张翻页感（横向位移 + 淡出，200ms）。
- 倒计时数字跨天变化：数字翻牌（flip），仅在跨天时触发一次。
- 全程尊重 `prefers-reduced-motion`。

## 3. 术语定义

| 术语 | 定义 |
| --- | --- |
| 倒计时（Countdown） | 以某个目标日期/时刻为终点的事项，核心展示"剩余天数" |
| 事件（Event） | 落在日历上的日程，可单日、可跨日区间、可带时间 |
| **议程事项（Agenda Item）** | **没有日期**的待办：一件要做但还没决定哪天做的事，由「标题 + 若干子项」组成（v1.2）。什么时候做已经定了的事应建成日历事件 |
| 标记（Marker） | 日历格上的小色点/色条，用于指示当日存在倒计时或事件 |
| 区间事件 | `start != end` 的跨日事件，在日历上以横条跨格呈现 |
| 今日格 | 月/周视图中代表当天的单元格，使用淡黄便签底色 |
| 农历层 | 叠加在公历之上的农历日、节气、节日、调休信息 |

**卡片信息层级（自上而下）**

1. 剩余天数 / 大字时钟（最大字号，朱砂红）
2. 内联跳动时钟 `HH:MM:SS`，接在「剩余 N 天」之后（仅当剩余 > 1 天且设了时间）
3. 标题（衬线，中号）
4. 目标日期 + 目标时间 / 全天（淡墨，小号，`2026-06-07 周日 · 09:00`）
5. 可选：标签色条、进度条

**倒计时显示状态机**

| 形态 | 条件 | 主视觉 | 副行 |
| --- | --- | --- | --- |
| 全天 · 未来 | 未设时间，`d > 0` | `剩余 N 天` | — |
| 全天 · 今日 | 未设时间，`d == 0` | `就是今天` | — |
| 全天 · 已过 | 未设时间，已过当天 | `已过去 N 天` | — |
| 精确 · 未来 | 设了时间，`d > 0` | `剩余 N 天 HH:MM:SS` | 同一行，无「还有」前缀 |
| 精确 · 24h 内 | 设了时间，`d == 0` | **`HH:MM:SS`（大字）** | — |
| 精确 · 已过 | 设了时间，`d > 0` | `已过去 N 天` | `已过 HH:MM:SS` |
| 精确 · 刚过 | 设了时间，`d == 0` | **`HH:MM:SS`（大字）** | — |

**状态定义**

| 状态 | 条件 | 表现 |
| --- | --- | --- |
| 未来 | `target > now` | 朱砂红天数 / 大字时钟 |
| 24h 内 | 同一日历日 | 淡黄便签底 + 大字 `HH:MM:SS` |
| 已过期 | `target <= now` | 灰色，`已过去 N 天` / `已过 HH:MM:SS` |

> **为什么日期/时间必须自绘**：用「透明 + `opacity:0` 的原生 input 覆盖在胶囊上」的写法，在 WKWebView 里点击后**没有任何视觉反馈**——用户会直接判定为「点不动、选不了时间」。自绘浮层同时满足 §6.5「指针优先」：全部靠点选完成。

> **为什么确认弹窗必须自绘**：Tauri 用的 wry 在 macOS 上只实现了 `runOpenPanelWithParameters`（文件选择），**没有实现** `runJavaScriptConfirmPanel`。按 WebKit 规范，UIDelegate 未实现该方法时 `window.confirm()` **不弹窗、直接返回 `false`**。这意味着 `if (confirm(...)) doDelete()` 里的删除**永远不会执行**，表现为「删除功能没实现」。所有原生 JS 弹窗一律禁用。

> **为什么浮层必须 portal**：CSS 规范规定，**任何非 `none` 的 `transform`（或 `filter` / `will-change`）都会让元素成为 `position: fixed` 后代的包含块**。事件抽屉的滑入动画是 `transform: translateX(...)`，而 `animation-fill-mode: both` 让该 transform 在动画结束后**依然保留**——于是抽屉里的选择浮层不再按视口定位，被推到屏幕外，表现为「点时间没反应」。
> 双重防护：① 抽屉动画的 `to` 帧写 `transform: none`；② 所有浮层走 `createPortal` 到 `document.body`，脱离任何 transformed 祖先。

### 6.5 指针优先交互规范

**原则：能用鼠标点，就不要求用户按键。**

| 类别 | 规范 |
| --- | --- |
| 主操作入口 | 每个功能都必须有**可见控件**：按钮、图标、菜单项、右键菜单 |
| 新建倒计时 | 左栏顶部输入区 + 明确的「添加」按钮（不按回车也能完成） |
| 新建事件 | 点日历格 → 浮出「＋ 新建事件」→ 点开表单 → 点「保存」 |
| 视图切换 | 日历区顶部一排**可点击的分段标签**：月 / 周 / 日；议程在顶栏独立成页 |
| 周期导航 | 标题两侧的 `‹` `›` 圆形按钮 + 「今天」按钮 |
| 日期跳转 | 点标题或标题旁的日历图标 → 弹出月历选择器 → 点选日期 |
| 编辑 / 删除 | 右键事件或倒计时卡片弹出上下文菜单；表单底部固定有「删除」「保存」按钮 |
| 关闭面板 | 点右上角「×」、点遮罩区、或按 `Esc`（三选一即可） |
| 滚动 | 触控板两指滑动 / 鼠标滚轮；滚动条在悬停时可见 |
| 悬停反馈 | 所有可点元素都有 hover 态与指针形状变化，明确"这里能点" |
| 底部兜底 | 不戴键盘也能完成：创建倒计时、创建区间事件、切换日历视图与议程页、跳转日期、编辑、删除、开关设置 |

**禁止**

- 不允许存在"只能通过快捷键触发"的功能。
- 不允许把主操作做成隐藏手势或长按才出现的隐蔽入口。
- 不依赖 `⌘` 组合键完成任何核心流程。
- 不做快捷键自定义（`SET-09` 已取消）。
- **不允许**用「透明覆盖的原生 `input[type=date|time]`」冒充按钮：点击无反馈，等于不可用。
- **不允许**出现只能靠键盘输入才能完成的必填项（日期、时间、颜色、开关一律可点选）。
- **不允许**使用 `window.confirm` / `window.alert` / `window.prompt`：Tauri 的 WKWebView 不支持，会静默返回 `false`，让功能看起来「没实现」。一律用站内弹窗。

## 7. 技术方案

### 7.1 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 应用框架 | **Tauri v2** | 体积小、内存低；使用 WKWebView，macOS 渲染与系统一致；Rust 侧负责 SQLite 与系统集成 |
| 前端 | **React 18 + TypeScript + Vite** | 生态成熟，日历交互与状态管理可控 |
| 样式 | **原生 CSS + CSS Variables（主题 token 层）** | 这套设计高度定制，原生 CSS 更直接；全部色值/圆角/阴影走变量，换主题零改组件 |
| 状态 | **Zustand** | 轻量，适合"倒计时 + 日历"局部状态 |
| 日期计算 | **date-fns** | 纯函数、体积小、时区可控 |
| 农历/节气/节日 | **lunar-typescript** | 本地计算，无网络依赖 |
| 存储 | **SQLite**（`tauri-plugin-sql` 或 Rust `rusqlite`） | 结构化查询、可靠持久化 |
| 图标 | **lucide-react**（描边风格） | 与手账/纸感克制风格一致 |
| 菜单栏常驻 | Tauri 菜单栏能力 + Rust 原生 `NSStatusItem` | 关闭窗口后仍在菜单栏运行 |
| 系统主题 | 监听 `NSAppearance`（`WindowEvent::ThemeChanged`） | 应用固定纸张浅色，但需读取系统外观以决定是否给出一次性说明 |
| 构建签名 | `tauri build` + ad-hoc `codesign` | 本地自用，无需 Apple Developer ID / 公证 |
| 安装 | `install.sh`（复制 `.app` 到 `/Applications` + 刷新 LaunchServices） | 一键把构建产物变成可日常双击的软件，见 §7.6 |

### 7.5 核心算法要点

| 问题 | 方案 |
| --- | --- |
| 月视图网格 | 以"周起始日"对齐；生成 6×7 = 42 个日期单元，覆盖前后月补位 |
| 区间事件排布 | 将区间事件按周切分为"段"；每段在列内按 `行索引` 分配泳道，避免重叠（类似甘特泳道算法） |
| 倒计时天数 | 以**本地日期**（非 UTC）为基准做 `differenceInCalendarDays`，避免跨时区/跨夏令时误差 |
| 跨天归零 | 应用常驻时用定时器在本地 00:00 触发重算；休眠唤醒后重新计算 |
| 农历显示优先级 | 节气 > 传统节日 > 公历节日 > 农历初一(月名) > 农历日 |
| 重复事件展开 | 查询区间内按 `repeat_rule` 展开为虚拟实例，编辑时区分"仅此一次 / 之后全部" |

### 7.6 本地构建、签名与安装（关键路径）

目标是：**不依赖 `tauri dev`，双击就能用的日常软件**。

**两种运行模式**

| 模式 | 命令 | 用途 | 菜单栏 |
| --- | --- | --- | --- |
| 开发模式 | `pnpm tauri dev` | 写前端、调 UI、迭代样式（热更新） | ❌ 系统行为不可靠，不要在此验证 |
| Bundle 模式 | `pnpm tauri build --debug` 后运行 `target/debug/bundle/macos/RunningDO.app` | 验证菜单栏与真实窗口行为 | ✅ 正常 |
| 发布模式 | `pnpm release` | 构建 release `.app` → 签名 → 安装到 `/Applications` | ✅ 正常 |

> **重要**：菜单栏与窗口行为依赖一个已注册的 `.app` bundle（bundle id + 签名 + LaunchServices 注册）；在 `tauri dev` 下直接跑裸二进制时系统行为往往不可靠，这是**环境问题而不是代码 bug**。与菜单栏、窗口有关的验收都要在 Bundle 模式或发布模式下进行。

**`scripts/release.sh` 建议流程**

```bash
#!/usr/bin/env bash
set -euo pipefail

APP_NAME="RunningDO"
BUNDLE_ID="com.charlezk9.runningdo"
INSTALL_DIR="/Applications"

# 1. 构建 release bundle（只针对本机 arm64）
pnpm tauri build --target aarch64-apple-darwin

APP_SRC="src-tauri/target/aarch64-apple-darwin/release/bundle/macos/${APP_NAME}.app"

# 2. 退出正在运行的旧版本，避免替换失败
osascript -e "tell application \"${APP_NAME}\" to quit" 2>/dev/null || true
sleep 1

# 3. ad-hoc 签名（本地自用足够）
codesign --force --deep --sign - "${APP_SRC}"
codesign --verify --verbose=2 "${APP_SRC}"

# 4. 安装到 /Applications
rm -rf "${INSTALL_DIR}/${APP_NAME}.app"
cp -R "${APP_SRC}" "${INSTALL_DIR}/"

# 5. 让 LaunchServices 重新识别（菜单栏 / 默认应用依赖这一步）
/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister \
  -f "${INSTALL_DIR}/${APP_NAME}.app"

# 6. 重新签名（cp 后确保签名未被破坏）
codesign --force --deep --sign - "${INSTALL_DIR}/${APP_NAME}.app"

open "${INSTALL_DIR}/${APP_NAME}.app"
echo "✅ ${APP_NAME} 已安装到 ${INSTALL_DIR}"
```

**`package.json` 脚本约定**

| 脚本 | 作用 |
| --- | --- |
| `pnpm dev` | 仅前端 Vite 开发服务器（不常用） |
| `pnpm tauri dev` | 开发模式（快速迭代 UI） |
| `pnpm bundle:debug` | 构建 debug bundle，用于验证菜单栏 |
| `pnpm release` | 构建 release + 签名 + 安装到 `/Applications`（§7.6 脚本） |
| `pnpm db:backup` | 手动导出 JSON 备份 |

**只做一件事的构建链路**：不启用开机自启、不请求任何系统权限，构建产物就是全部。

**升级流程**

重新执行 `pnpm release` 即可（脚本内含退出旧版本 → 替换 → 重签 → 重注册）。数据库在 `~/Library/Application Support/` 下，**不会被覆盖**。

## 11. 风险与开放问题

### 11.1 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 法定节假日/调休数据每年更新 | 角标可能过期 | 数据由 `lunar-typescript` 提供，更新需升级依赖并重新构建 |
| 农历库体积与精度 | 打包体积、极端日期边界 | 选用 `lunar-typescript`；对 1900–2100 范围做单元测试 |
| 区间事件排布算法复杂 | 月视图布局错乱 | 先实现简单泳道算法，边界情况收敛后再优化 |
| 时区/夏令时导致天数偏差 | 倒计时天数错误 | 统一使用本地日期语义计算，禁用 UTC 直接相减 |
| **开发模式（`tauri dev`）下系统行为不可靠** | 误以为菜单栏/窗口坏了，白排查 | 系统行为只在 `.app` bundle 中可靠；验证时用 **Bundle 模式**运行，见 §7.6 |
| ad-hoc 签名被破坏 | 应用无法正常启动（复制、改文件后签名失效） | 安装脚本在 `cp` 后**重新签名**；不手动修改 `/Applications` 内的文件 |
| 系统深色模式与纸张浅色冲突 | 深色下刺眼、预期不符 | 应用固定纸张浅色；首次在深色模式启动时给一次性说明 |
| **macOS 大版本升级后 API 行为变化** | 自用应用突然失效 | 系统大版本升级后跑一遍 §10 验收清单；构建与签名步骤保持可复现 |
| 数据库损坏 | 大量数据丢失 | 事务写入；升级新增表前自动落一份 JSON 兜底备份 |
| 纸张纹理影响性能 | 滚动掉帧 | 纹理用静态背景图或低成本 CSS，避免实时滤镜 |

| Q5 | 主题数量？ | **已定：先只实现一个主题**（宣纸）；但色板/圆角/阴影全部走 CSS Variables（theme token），**保留切换接口**，将来加第二主题只需换一份 token 文件 |
| Q6 | 数据是否需要加密？ | 默认不加密（本地个人数据） |
| Q7 | 是否需要应用内语言切换？ | 默认中文优先，预留结构 |
| Q8 | 目标平台？ | **已定：macOS 独占**，仅 Apple Silicon，不做 Windows / Linux / 移动端 |
| Q9 | 使用与分发方式？ | **已定：开发者本人自用，不对外分发**；本地构建 + ad-hoc 签名 + 安装到 `/Applications`；不做公证、不上架、不做自动更新 |
| Q10 | 关闭主窗口的行为？ | 默认隐藏窗口、菜单栏常驻，不退出应用；设置中可改为「关闭即退出」 |
| Q12 | 是否需要 `.ics` 导出？ | **已定：不需要**。`.ics` 是日历交换格式（RFC 5545），用于导入 Apple/Google/Outlook 日历；自用场景无用。只做 JSON 备份导出（验证防丢 + 可迁移到另一台 Mac） |
| Q13 | 兼容的 macOS 版本？ | **已定：以开发机当前版本为准（macOS 26.6.2 / Apple M5 / arm64）**，不向下兼容 |
| Q14 | — | 已被 Q5 合并：先做单一主题 + 保留切换接口 |
| Q15 | 快捷键策略？ | **已定：尽量不使用快捷键**。所有功能提供可见指针入口；系统自动为菜单分配 `⌘` 快捷键属 macOS 行为，保留但**不作为使用路径、不做自定义**（`SET-09` 已取消） |
